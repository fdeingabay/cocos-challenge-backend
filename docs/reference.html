Datos

Lo que dice database.sql

Cuatro diferencias entre el enunciado y el DDL real que cambian decisiones de código.

HallazgoImpacto en el desarrollo
marketdata tiene date DATE, no datetime TIMESTAMP El listado del enunciado no coincide con el DDL. Hay 2 fechas: 2023-07-13 y 2023-07-14.
Postgres pliega identificadores sin comillas a minúsculas Las columnas reales son instrumentid, previousclose, accountnumber. EF Core necesita HasColumnName explícito en todo.
Cero índices, cero NOT NULL, cero CHECK Todo es VARCHAR nullable. No hay ninguna defensa a nivel base.
CASH_IN/CASH_OUT usan instrumentId 66 (ARS), size=monto, price=1 monto = size × price de forma uniforme para todos los sides. Un solo cálculo sirve para todo.

Inconsistencia detectada en el seed

El usuario 1 tiene una posición negativa en BMA:

Instrumento 31 (BMA)   BUY  20 @ 1540  FILLED   →  +20
                       SELL 30 @ 1530  FILLED   →  −30
                                       ──────────────────
                                         posición   −10  ← imposible

Existe una BUY 60 @ 1500 en estado NEW que solo cerraría el número si se contaran las NEW — cosa que el enunciado prohíbe explícitamente. Dato sucio o trampa deliberada: se documenta en el README y no se toca el seed. Es exactamente el bug que toda la arquitectura busca prevenir, ya presente en los datos de entrada.

Escritura

Cómo se ejecuta una orden

Todo ocurre dentro de una única transacción, sostenida por un lock de la cuenta tomado antes de leer nada.

Tabla de decisión

TipoSideSe valida contraAlcanzaNo alcanza
MARKETBUYcash disponible ≥ size × close FILLED descuenta cash, suma accionesREJECTED
MARKETSELLtenencia disponible ≥ size FILLED suma cash, resta accionesREJECTED
LIMITBUYcash disponible ≥ size × precioLímite NEW reserva cash, no mueve nadaREJECTED
LIMITSELLtenencia disponible ≥ size NEW reserva acciones, no mueve nadaREJECTED
FILLED → el movimiento YA ocurrió. Afecta cash y tenencia reales. NEW → el movimiento VA A ocurrir. Solo reserva. No mueve nada todavía.

Orden enviada por monto

{ "instrumentId": 47, "side": "BUY", "type": "MARKET", "amount": 100000 }

  close de PAMP(47) = $925,85
  cantidad = floor(100.000 / 925,85) = floor(108,01) = 108 acciones
  costo real = 108 × 925,85 = $99.991,80
  sobran $8,20 sin usar — no se admiten fracciones de acción

Si floor(monto/precio) == 0 devolvemos 400: no es falta de fondos, es una orden que no se puede formar. Persistirla ensuciaría el libro.

Lectura

Cómo se calcula el portfolio

No hay saldo almacenado: todo el estado del usuario es una proyección de la tabla orders.

CASH contable = + CASH_IN − CASH_OUT + SELL FILLED − BUY FILLED (size × price) disponible = contable − reservas de BUY en NEW POSICIONES cantidad = + BUY FILLED − SELL FILLED disponible = cantidad − reservas de SELL en NEW valor = cantidad × close ppp = Σ(BUY filled: size × price) / Σ(BUY filled: size) rend.total = (close − ppp) / ppp × 100 rend.día = (close − previousClose) / previousClose × 100 VALOR TOTAL DE CUENTA = cash contable + Σ(valor de cada posición)

El rendimiento total es contra el costo promedio ponderado, no contra previousClose. Son dos métricas distintas: el rendimiento es del usuario, el retorno diario es del instrumento y todos ven el mismo. Se devuelven como campos separados.

Y todo esto en una sola query

FROM orders o
JOIN instruments i ON i.id = o.instrumentid
LEFT JOIN LATERAL (
    SELECT "close", previousclose
    FROM   "marketdata" m
    WHERE  m.instrumentid = i.id
    ORDER BY m."date" DESC
    LIMIT  1                      -- resuelve "2 días por instrumento"
) md ON true
WHERE o.userid = @userId
GROUP BY i.id, i.ticker, md."close", md.previousclose

El LATERAL es lo que evita el N+1 y el JOIN duplicado. Sin él, o hacés una query por instrumento, o traés las 2 filas de marketdata y duplicás cada posición.

Concurrencia

Cómo se mantiene la consistencia

Dos invariantes que no pueden violarse nunca, bajo ninguna secuencia de operaciones concurrentes.

cash_disponible(user) >= 0 tenencia(user, instrumento) >= 0

Los tres mecanismos

MecanismoQué problema resuelveCómo
Lock por cuenta Dos órdenes simultáneas del mismo usuario gastan el mismo peso SELECT … FROM user_accounts WHERE userid=@u FOR UPDATE al inicio de la transacción
Reservas en el disponible Órdenes NEW comprometen fondos que nadie descuenta El disponible resta las NEW de BUY (cash) y de SELL (acciones)
UPDATE condicional Cancelar dos veces, o cancelar algo ya ejecutado UPDATE … WHERE id=@id AND status='NEW' → verificar rowsAffected == 1
Idempotency-Key Un reintento del cliente crea una orden duplicada UNIQUE (userid, idempotencykey) — la orden es su propio registro de idempotencia
CHECK constraints Un bug de código se cuela igual La base rechaza. Última línea de defensa.

Como no simulamos el mercado no hay matching entre usuarios, así que las cuentas son independientes: el lock por usuario no genera contención entre usuarios distintos.

Lo que deliberadamente no cambiamos

No se agrega tabla de balances materializados: el enunciado pide explícitamente calcular tenencia y disponible desde orders, y respetarlo es parte del ejercicio.
